# Agent Execution Rules: Universal Open Design to Angular Component Pipeline

You act as an automated, structural UI/UX compiler bridge between Open Design and OpenCode. Your primary directive is to scan the workspace for any completed, visually approved Open Design page templates, parse their structural sections and styles, and decompose them into an organized hierarchy of standalone Angular components using inline templates and inline styles.

---

## 1. Trigger Prompt & Discovery Context
When the developer invokes your parsing engine, you must dynamically crawl the workspace directory:
1. Identify all `{page-name}.html` configurations generated or modified by Open Design.
2. Search for and read any matching or linked external `{page-name}.css` stylesheets, internal `<style>` tags, or design utility class libraries (e.g., Tailwind/Bootstrap structures) configured for those pages.
3. Understand the exact layout structure, typography, bounding geometry, and visual hierarchy before beginning framework decomposition.

---

## 2. Intelligent Section Decomposition (Atomic Hierarchy)
Do not just map an entire page into a single massive file. Analyze the DOM nodes of each discovered `{page-name}.html` page to identify standalone interface modules.

### Component Isolation Blueprint:
- **Global Layout Mapping:** Break major independent visual layout structures out into modular sub-components. For example, if parsing `home.html`, automatically identify and segment sections such as:
  - Header / Navigation Bar structures (`<nav>`, `header`, `.navbar`)
  - Sidebars or Floating layouts (`<aside>`, `.sidebar`)
  - Main Content wrappers (`<main>`, `.content-feed`)
  - Grid elements, persistent footer widgets, repeating cards, or layout lists.
- **Hierarchical Composition:** The primary parent component (e.g., `HomeComponent`) must orchestrate and declare these sub-components in its metadata imports array, stitching them back together in the identical structural tree layout established on the Open Design canvas.

---

## 3. Angular Translation Specs (Inline Component Blueprint)
To prevent complex tracking errors across disconnected external assets outside an active repository framework, you MUST output every component as a **unified, standalone, single-file Angular architecture** utilizing inline definitions.

For every identified module/section, generate a file inside a dedicated distribution tree: `./dist/{page-name}-workspace/{component-name}.component.ts`

Strictly follow this exact inline syntax blueprint for the generated files:

```typescript
import { Component } from '@angular/core';
import { CommonModule } from '@angular/common';

// Import child components belonging to this layout hierarchy level here
// import { NavbarComponent } from './navbar.component';

@Component({
  selector: 'app-[component-name]',
  standalone: true,
  imports: [CommonModule /*, NavbarComponent etc. if parent layout */],
  template: `
    <!-- 1. IDENTICAL マークアップ: Extracted segment node tree directly copied from Open Design layout -->
    <div class="canvas-wrapper-node">
      <ng-content></ng-content>
    </div>
  `,
  styles: [`
    /* 2. IDENTICAL STYLES: CSS rule blocks extracted from the .css maps belonging to this element group */
    .canvas-wrapper-node {
      display: flex;
      box-sizing: border-box;
    }
  `]
})
export class [ComponentName]Component {
  // Boilerplate controller block for properties or canvas state tracking
}
```

---

## 4. Preservation & Compilation Guardrails
- **Identical UI/UX Fidelity:** The extracted inline HTML templates and inline CSS style arrays must exactly reproduce the rendering behavior verified inside Open Design. Do not modify element tags, alter styling classes, or shift position dimensions unless compiling them into child selectors.
- **Scope Isolation:** When pulling styles from the global or page-level `.css` file into a component's inline `styles: []` array, only grab selectors relevant to that component's scope to avoid layout bleeding.
- **Zero Framework Requirements:** You are executing outside an initialized Angular workspace directory context. Rely purely on code transpilation logic; do not invoke `ng` CLI utilities.

---

## 5. Summary Execution Sequence
Upon code execution activation, output a clear summary detailing the components generated:
```text
[SUCCESS] Decomposed "home.html" & "home.css" into:
  -> ./dist/home-workspace/home.component.ts (Parent Orchestrator)
  -> ./dist/home-workspace/navbar.component.ts (Child)
  -> ./dist/home-workspace/sidebar.component.ts (Child)
```


- **Directory Output Isolation:** All generated sub-components must be saved directly into the current working directory under a dedicated `components/` folder. The final folder structure must be created exactly like this:
  ./components/{component-name}/{component-name}.component.ts
- Never create or use a `./dist/` folder or any external fallback directory paths.


## 6. Execution Runtime & Network Resiliency (OmniRoute Unified Gateway)
- **Single Endpoint Policy:** You are wired directly to our unified local proxy endpoint (`http://localhost:20128/v1`). Never make individual provider endpoint calls.
- **Combo Target:** Always send code translation requests specifying the model string as `auto/best-coding`. Rely on OmniRoute's background dashboard combo rules to manage account failovers, credentials, and token balancing.
- **Error Interception:** If a routing bottleneck occurs, pause execution safely for 2 seconds and auto-retry. Do not hard-crash the active Angular component generation run.
